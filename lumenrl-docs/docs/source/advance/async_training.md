# Asynchronous Training

Synchronous RL alternates: the rollout generates a batch, the trainer trains on
it, the new weights go to the rollout, and every GPU waits for the slowest
response in between. LumenRL's Ray controller path can instead give the rollout
GPUs of its own and keep it generating while the trainer trains, in two ways
modeled on verl:

| Mode | Switch | What overlaps | verl counterpart |
| --- | --- | --- | --- |
| One-step off-policy | `controller.ray.one_step_off_policy: true` | Step *s+1*'s batch generates while step *s* trains | `one_step_off_policy` |
| Fully async | `controller.ray.fully_async.enabled: true` | Prompt groups stream to the trainer as they finish; generation runs ahead by a budgeted amount | `fully_async_policy` |

Both train on data generated by slightly older weights and rely on the rollout's
own log-probs (`calculate_log_probs: true`) with rollout correction (TIS) to
correct for it.

## Requirements

- The Ray controller (`controller.ray.enabled: true`) with the vLLM rollout
  (`generation_backend: vllm`, `vllm_cfg.transport: ray_http`). Both modes
  have been run with the FSDP2 training backend.
- Or the ATOM rollout (`generation_backend: atom`, `atom_cfg.transport:
  ray_http`). Its RCCL weight sync and `fully_async.partial_rollout` need an
  ATOM build with the RCCL weight receive and the engine's `pause_generation`
  (mode `keep`): ATOM's pause PR
  ([ROCm/ATOM#3059](https://github.com/ROCm/ATOM/pull/3059)) and its RCCL-receive
  PR ([ROCm/ATOM#3058](https://github.com/ROCm/ATOM/pull/3058)).
  An older ATOM fails at start with `weight_sync.backend: rdma`, as it
  cannot report RDMA support, and is refused partial rollout; run it with
  `weight_sync.backend: shared_folder` and `partial_rollout: false`, and each
  sync waits for the groups in flight and goes through shared memory (about
  33 s for Qwen3-8B).
  `run_dapo.sh` turns sleep mode on for `MODE=atom*` (a colocated rollout
  frees its memory for training); pass
  `policy.generation.vllm_cfg.enable_sleep_mode=false`.
- A rollout pool of its own: `controller.ray.rollout.num_workers > 0`, with the
  actors on the remaining GPUs (`controller.ray.actor.num_workers`), for example
  4 + 4 on one 8-GPU node.
- `vllm_cfg.enable_sleep_mode: false`: the rollout never stops between steps.
- Weight sync over RCCL (an older ATOM aside): `weight_sync.backend: rdma`. On
  a single node this is GPU P2P, so set `weight_sync.rdma.require_rdma: false`;
  set `weight_sync.rdma.interface` and `weight_sync.rdma.hca` to the node's NIC
  and HCA either way. A sync of Qwen3-30B-A3B (61 GB in BF16) takes about 2 s.

Setups that cannot overlap are rejected when training starts: both switches
on, no separate rollout pool, a sleeping rollout, and for fully async also
partial rollout on an ATOM that cannot pause generation, and `moe.r3`
(routing replay is not carried across a weight sync).

## One-step off-policy

```yaml
controller:
  ray:
    one_step_off_policy: true
```

While step *s* trains, step *s+1*'s batch (including DAPO's `filter_groups`
regeneration rounds) generates on the rollout pool; the weights are synced after
every step. Every batch after the first trains one update after the weights
that generated it. This hides the training time behind generation, but not the
other way round: when generation is the slow part, the gain is small.

## Fully async

```yaml
controller:
  ray:
    actor:
      num_workers: 4
    rollout:
      num_workers: 4
    fully_async:
      enabled: true
      trigger_parameter_sync_step: 1
      staleness_threshold: 1.0
      partial_rollout: true
```

| Key | Default | Meaning |
| --- | --- | --- |
| `enabled` | `false` | Turn fully async on; exclusive with `one_step_off_policy` |
| `trigger_parameter_sync_step` | `1` | Optimizer steps between two weight syncs (*K*) |
| `staleness_threshold` | `0.0` | Per sync period the rollout budgets `(1 + s) × groups per step × K` useful prompt groups, counting those still queued from before the sync (*s*) |
| `partial_rollout` | `false` | On a sync, freeze the requests in flight and continue them on the new weights, instead of waiting for them to finish |
| `max_inflight_groups` | `0` | Prompt groups generating at once; 0 means `max_num_seqs // n` per replica |
| `overlap_validation` | `false` | Validate on a background thread while training goes on, instead of holding the trainer for it (see below) |

### How it works

A background thread (`StreamingRollout` in
`lumenrl/trainer/fully_async_rollout.py`) keeps prompt groups (one prompt ×
`num_generations`) in flight:

1. Each group goes, whole, to the replica with the fewest groups in flight.
2. Groups are collected in the order they finish, scored, and filtered one at a
   time by DAPO's `filter_groups`. Kept groups enter a queue tagged with the
   weight version that started them.
3. The trainer takes one step's worth of groups (`train_global_batch_size /
   num_generations`), merges them into a batch, and from there trains exactly as
   the synchronous loop does.
4. Every *K* updates the trainer syncs the weights. With `partial_rollout`, the
   engines are paused with vLLM's `pause_generation(mode="keep")`: requests in
   flight are preempted and, after `resume_generation()`, re-prefilled and
   continued on the new weights, with no resubmission. Without it, the sync
   waits for the groups in flight to finish.

The budget counts the groups queued from before the sync, the groups kept since
it, and the groups in flight weighted by the recent keep rate. Groups dropped by
`filter_groups` do not count, so a run of dropped groups cannot leave the
trainer waiting on a rollout that believes it is ahead. The budget is an
expected count, not a cap: when more of the groups in flight are kept than the
keep rate predicts, a period ends over budget. This shows most at a sync without
partial rollout, which waits for every group in flight; in a six-step example 6
smoke at *K* = 2, `s = 1`, the first period kept 42 groups against a budget of
32.

Validation runs on the rollout pool. By default the trainer waits for it and
new submissions are held back meanwhile. Its length is that of the longest
response, so more replicas do not shorten it: on example 6 it takes about 500 s
on 4 or 8 replicas.

With `overlap_validation`, a validation step starts validation on a background
thread instead, and training and new submissions go on beside it. Validation
requests share the replicas with the training groups. With partial rollout a
weight sync freezes them along with the groups, so the long responses finish on
newer weights; `val/finished_version` minus `val/started_version` counts the
syncs a validation ran through. Without partial rollout the next sync waits for
validation to finish, since the engine loads weights only when idle. Metrics
are logged at the first step after validation finishes, with `val/global_step`
naming the step validated. One validation runs at a time: a due step waits for
the one running before it starts its own. The last step validates in the
foreground; when it does, the step before waits for the one running, so the
two are not logged on the same step.

On resume from a checkpoint the prompt cursor skips the prompts the run has
used, estimated as one `gen_batch_size` round per step. Groups that were queued
or in flight at the checkpoint are not saved; the resumed run generates new
ones.

### What staleness means here

- A group's staleness is the number of updates between the weights that
  *started* it and the step that trains on it. With partial rollout most of its
  tokens may come from newer weights, so this is an upper bound.
- `staleness_threshold: 0` is not strictly on-policy: groups still generating
  at a sync, and the extra groups submitted to make up for dropped ones, train
  one update late. With *K* > 1 the later updates of a period also reuse the
  period's weights, so staleness grows to *K* − 1 within it.
- Staleness is therefore not a hard bound. The over-budget period above trained
  groups 5 updates after the weights that started them (*K* = 2, `s = 1`,
  where a period on budget stays at 3 or below); `async/staleness_max` shows
  when it happens.
- Every token's rollout log-prob is the probability it was actually sampled
  with, so TIS corrects the right ratio whatever the staleness.

### Metrics

| Metric | Meaning |
| --- | --- |
| `async/staleness_mean`, `async/staleness_max` | Staleness of the step's groups |
| `async/partial_groups` | Groups that spanned a weight sync |
| `async/trainer_wait_s` | Seconds the trainer waited for groups, plus the wait for groups in flight at a sync without partial rollout |
| `async/queued_groups`, `async/inflight_groups` | Groups ready and generating when the step's groups were taken |
| `async/keep_rate` | Fraction of finished groups `filter_groups` kept |
| `val/global_step` | With `overlap_validation`: the step whose weights started the validation logged at this step |
| `val/started_version`, `val/finished_version` | Rollout weight versions when that validation started and finished |
| `val/elapsed_s` | How long it ran; `timing_s/testing` counts only the seconds the trainer waited for it |

### Tuning

- The rollout keeps the trainer fed when `staleness_threshold` is about one
  group's generation latency divided by the training step time. On example 6
  a group takes 90–150 s and a step trains in 20–30 s, so `s = 1–2` with
  partial rollout. `async/trainer_wait_s` near zero means the rollout keeps up.
- Without partial rollout the long tail of the groups in flight holds every
  sync; at `s = 0` that is slower than synchronous training.
- Raise `vllm_cfg.max_num_seqs` so each replica can keep enough groups in
  flight; example 6 uses 512 (32 groups of 16 per replica).
- `trigger_parameter_sync_step > 1` syncs less often at the price of staler
  data; with syncs of about 2 s there is little to save at *K* = 1.
- Groups in flight are capped twice, by the budget and by
  `max_inflight_groups`; raise `max_num_seqs` with `s`, or the cap stays at
  `max_num_seqs // n` per replica (see the two-node results).
- `overlap_validation` pays off when validation is long and `val_steps`
  training steps take longer than one validation; otherwise the next due step
  waits for the rest of it.

## Results

Example 6 (Qwen3-30B-A3B-Base, DAPO on DAPO-Math-17k) on one node of 8×
MI355X, image `dapo-gfx950-rocm7.2.3-260921b`.

### Smoke runs

Six steps of `dapo_qwen3moe_a3b_ray_vllm_verlref_4k_smoke.yaml`: the long run's
hyperparameters below at a smaller scale (8 prompts × 16 rollouts,
`gen_batch_size: 24`, 4096-token responses, `max_num_batched_tokens: 8192`, no
validation). Every row runs on 4 + 4 GPUs: 4 actors, 4 vLLM replicas with
`gpu_memory_utilization: 0.85` and `max_num_seqs: 256`, RCCL weight sync.

## Limitations

- `trigger_parameter_sync_step > 1` has been run end to end only in six-step
  smoke runs (*K* = 2, with and without partial rollout); the long runs above
  use *K* = 1.
- Per training step, fully async can learn somewhat less than synchronous
  training. On a longer run outside example 6 (Qwen3-8B, multi-turn tool calls,
  150 steps, `s = 1`, partial rollout) its AIME24 trailed by 0.03–0.07 from step
  90 on, while it reached step 150 in 258 min against 640 min. Compare runs at
  equal wall-clock time as well as at equal steps.
- The rollout's queue and in-flight groups are not checkpointed, and the
  resumed prompt cursor is an estimate (see above).
- No decoupled PPO: the trainer recomputes the old log-probs with its current
  weights and TIS corrects against the rollout's.
- Rejected with fully async: partial rollout on an ATOM without
  `pause_generation`, and MoE routing replay (`moe.r3`). Untested: the Megatron training backend. The two-node layout
  has run 30 steps at most.

## The `async_training` section

`async_training.enabled` selects `AsyncRLTrainer`, an earlier design that is
superseded by the modes above: it generates and trains in turn on the same
GPUs, and its rollout engine never loads the updated weights. It logs a warning
when used; switch to `controller.ray.fully_async` or
`controller.ray.one_step_off_policy`.
